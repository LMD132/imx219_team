# 运行期调参通道（UART + PC 界面）

**一句话**：插上 USB 串口线（COM5），运行 `python tools/alg_tuner.py`，
拖动滑块 → 屏幕**立即**变化，**不需要重新编译，也不需要重新烧录**。

---

## 1. 为什么现在可以实时调

`rtl/algo/alg_top.v` 的每一个可调参数本来就是**运行期输入端口**
（`cfg_mode / cfg_t / cfg_lo / cfg_hi / cfg_median_en / cfg_gauss_en /
cfg_isol_en / cfg_disp_mode / cfg_ov_color`），不是综合期常量。
2026-09-27 又加了第 10 个：`cfg_eps`（NMS 容差，见 §3.2）。

以前"调参 = 改 Verilog → 编译约 2 分钟 → 烧录约 1 分钟"，原因只有两个：
顶层把这些端口**接成了常量**，而且板上没有参数输入通道。二者都在
2026-09-26 补上了：

```
PC (tools/alg_tuner.py)  --USB-->  FT4232H ch.C  -->  板 UART (GPIOR_28 / GPIOL_02)
                                                             |
                                                       alg_cfg_uart.v   (CLK_25M 域的寄存器组)
                                                             |
                                                       alg_cfg_sync.v   (跨到 HDMI 像素时钟域)
                                                             |
                                                       alg_top 的 cfg_* 端口  -->  画面
```

**这条通路本身没有引入任何新算法。** 参数名、位宽、默认值与之前写死的常量
**逐一对应**；不接串口时行为与旧版一致。

算法侧唯一的改动是 2026-09-27 给 NMS 加的容差端口 `cfg_eps`（§3.2）——
**默认 0，此时 `alg_nms.v` 的输出仍然与参考算法逐位一致**（由
`sim/algo/model/check_py_repo.py` 与 `check_chain.py` 双重复核）。

## 3. 命令协议（`rtl/alg_cfg_uart.v`）

一行一条（或一行多条），以 LF 或 CR 结束：

| 命令 | 参数 | 取值范围 | 默认值 |
| --- | --- | --- | --- |
| `M<n>` | `cfg_mode` | 0=单阈值 Sobel，1=双阈值 Sobel，2=Canny（>2 截到 2） | 2 |
| `T<n>` | `cfg_t` 阈值（仅 SOBEL 单阈值档用） | 0..2047（该档量程 0..2040） | 24 |
| `L<n>` | `cfg_lo` 滞后低阈值 | **0..255**（CANNY 档） | 21 |
| `H<n>` | `cfg_hi` 滞后高阈值 | **0..255**（CANNY 档） | 58 |
| `E<n>` | `cfg_eps` NMS 容差 | 0..8（>8 截到 8，仅 CANNY 档有效） | 0 |
| `P<n>` | `cfg_epf` 前置滤波档（EPF） | 0=关，1=3×3 高斯，2=导向滤波（>2 截到 2） | 0 |
| `F<n>` | `cfg_gf_eps` 导向滤波正则项 eps | 0..2047（参考值 400，仅 EPF=2 档有效） | 400 |
| `A<n>` | `cfg_temp` 时域降噪强度（TEMP） | 0..90（>90 截到 90；0=关=逐位直通当前帧） | 0 |
| `N<n>` | `cfg_median_en` 中值使能 | 0/1 | 1 |
| `G<n>` | `cfg_gauss_en` 5×5 高斯使能 | 0/1 | 0 |
| `I<n>` | `cfg_isol_en` 去孤点使能 | 0/1 | 1 |
| `D<n>` | `cfg_disp_mode` 显示模式 | 0..3 | 0 |
| `C<n>` | `cfg_ov_color` 彩色叠加 | 0/1 | 1 |
| `R` | 全部恢复开机默认值 | — | — |
| `X<n>` | 回读摄像头寄存器组 `<n>`（0..78），结果显示在状态行末尾 `CAM` 字段 | — | — |

分隔符宽松：`T24`、`T=24`、`T 24` 等价；字母大小写均可。
数值是**饱和累加**，所以 `T9999` 得到 2047 而不是回绕。
一行可以写多条：`T7 L8 H9`。无法识别的键（如 `Q`）被忽略，不影响其它命令。

### 3.0 阈值的量纲：为什么 `L` / `H` 是 0..255，而 `T` 是 0..2047

**这两个范围不一样，是因为它们比较的对象不一样。** 见 `rtl/algo/alg_top.v`：

```verilog
wire [10:0] thr_mag = (cfg_mode_d == 2'd2) ? {3'b0, nms_d} : sob4_mag;
```

| 显示/算法档 | 阈值级比较的对象 | 位宽 | `T` | `L` / `H` |
| --- | --- | --- | --- | --- |
| mode 2 CANNY（当前） | NMS 输出 `nms_d`，`clip(m,0,255)` | 8 bit | 不用 | **0..255** |
| mode 1 SOBEL 双阈值 | Sobel 全量程 `\|Gx\|+\|Gy\|` | 11 bit | 不用 | 0..2040 |
| mode 0 SOBEL 单阈值 | Sobel 全量程 `\|Gx\|+\|Gy\|` | 11 bit | 0..2040 | 不用 |

所以：

- **`L` / `H` 在 CANNY 档的真实量纲就是 0..255**（NMS 输出已经被 `clip(m,0,255)` 压到 8bit），
  GUI 滑块因此按 0..255 给。
- **`T` 只在 SOBEL 单阈值档生效**，那一档比较的是 11bit 全量程梯度（0..2040），
  所以 `T` 的滑块仍保留 0..2047，**不要跟着改成 255**，否则那一档永远只能取到很低的门限。
- **换成 mode 1（SOBEL 双阈值）时，滑块上限 255 不够用**：那一档的梯度能到 2040。
  串口命令不受影响（RTL 仍接受 0..2047），只是滑块拖不到。要那一档用滑块的完整量程，
  说一声我把上限定成随档位自动切换。

协议层（`alg_cfg_uart.v`）对 `L`/`H` 的饱和上限仍是 2047 —— 因为矢量对同一份 RTL 的
两种档位共用，限制在 2047 对两档都安全。GUI 收窄到 255 纯粹是为了**拖动精度**：
原来 2047 个档位摊在同一条滑块轨道上，鼠标每移一个像素就要跨好几个值，
很难停在 27、31 这种具体数字；收到 0..255 之后同样的轨道只需走约 1/8 的行程，
可以逐 1 调到任意值。（这个比例与窗口宽度无关，不会随窗口大小变化。）

### 3.1 状态回读（遥测）

板子每 **500 ms** 主动发一行状态，收到命令后**立即**再补发一行：

```
M2 T0024 LO0021 HI0058 MED1 GAU0 ISO1 DSP0 OVC1 EPS0 EPF2 GF0400 TMP00 CAM0077=C0\r\n
```

固定 **83 字节**（字段是逐次追加的，每次只插在 `CAM` 之前，所以已有字段的字节位置
一个都没动）：

| 追加批次 | 字段 | 追加后行长 |
| --- | --- | --- |
| 2026-09-27 | `EPS<n>` 插在 `OVC` 与 `CAM` 之间 | 65 字节 |
| 之后（`P`/`F` 命令那轮） | `EPF<n>`、`GF<nnnn>` 追加在 `EPS` 之后 | 77 字节 |
| 2026-09-28（本轮 TEMP） | `TMP<nn>` 追加在 `GF` 之后、`CAM` 之前 | **83 字节** |

`CAM` 永远是最后一个字段，`X<n>` 的回读结果留在原位。
这就是 GUI 右边"板端"那一列的来源 —— 用它来自证链路真的通了，
而不是只看 PC 单方面发出去了什么。

新增字段在 PC 侧正则里都是**可选**组：`EPF`/`GF`/`TMP` 缺失时，
界面相应那一行显示 `--` 而不是报"不一致"，所以本界面可以直接连旧的
77 / 65 / 60 字节位流继续调试，不会因为位流没更新就变红。

### 3.2 `E<n>`：NMS 容差（2026-09-27 新增，治"轮廓线上下流动"）

**现象**：Canny 档下轮廓线不是一条稳定的线，而是由许多短线段拼成，
上下跳动、像有电流在流动；调暗灯光能去掉小噪点，但**掉线和抖动与亮度无关**。

**根因**（离线用参考 Python 算法定量验证）：NMS 判决是"中心像素与梯度方向两侧
邻居比大小"，在**半像素相位**处，两个候选像素的梯度只差 1~几个 LSB，
噪声一推就翻面 → 线在相邻格之间来回跳。SOBEL 档不抖是因为它**没有 NMS**；
cv2.Canny 不抖是因为它沿真实梯度方向做插值比较，而不是二选一。

**对策**：给 NMS 判决加容差 `eps`，比较从 `m > 邻居` 放宽成 `m + eps > 邻居`
（`rtl/algo/alg_nms.v`）。等于**允许近等值的两个像素都保留**，线不再被噪声
推来推去。实测（同一斜边、两份独立噪声、逐行比较线的位置）：

| 条件 | 位置跳动行占比 | 线宽 |
| --- | --- | --- |
| eps=0（参考算法） | 10.0 % | 1.00 px |
| **eps=1** | 4.0 % | 1.12 px |
| **eps=2** | 1.0 % | 1.21 px |
| **eps=3** | 0.3 % | 1.32 px |
| 时域融合 4 帧（单独用） | 10.7 %（**无效**） | 1.00 px |

结论：**ε 能压掉约 90% 的流动抖动，代价是线宽从 1.0 px 变成 1.2~1.3 px。**
建议从 1 试到 3。注意两点：

1. **斜线固有的台阶**（理论 1 px 细线斜着画每跨一格就有 1 px 台阶，
   实测残差平均 0.27 px）删不掉，cv2.Canny 也一样，别把它当故障。
2. 时域融合治不了这个抖动（上表最后一行）—— 但 2026-09-28 重新在**真实
   像素流 + 真噪声**上测过，噪声主导的那部分抖动确实降了：`σ=16` 噪声下
   线位置翻转率 `TEMP=0` 时 117.0 → `TEMP=30` 时 34.2。两条结论不矛盾：
   ε 治的是**半像素相位**引起的翻面，TEMP 治的是**随机噪声**引起的翻面。

### 3.3 `A<n>`：时域降噪 TEMP（2026-09-28 新增）

**语义**：与参考 Python `temporal_blend()` 一致 ——
`alpha = 1 - TEMP/100`，`out = alpha*cur + (1-alpha)*prev`，
`TEMP` 越大当前帧权重越小、越稳，但运动物体拖影越明显。
仓库 `config.json` 的定稿值是 `temp=50`。

**当前 RTL 的默认值是 0（直通）**，不是 50：这样刷完新位流首屏和上一版
逐像素一致，方便快速判断"新加的东西有没有弄坏画面"；要等价于参考定稿值，
把滑条拉到 50 即可（`A50`）。

实现、定点格式、为什么在 Bayer 域融合、双基址交替读时序、
实测资源与时序，全部写在 `docs/时序降噪_移植说明.md`，这里不重复。

| 项 | 值 |
| --- | --- |
| 命令 | `A<n>`，0..90（>90 截到 90） |
| 上电默认 | 0（= 逐位直通当前帧，等价旧位流） |
| 参考定稿值 | 50 |
| 生效条件 | 需要本次带双基址 DDR 读的位流；旧位流里没有这条命令 |
| 已知代价 | 运动拖影（参考算法固有取舍，TEMP 越大越明显） |
| 显示侧 | HDMI 输出仍是 RGB565 降位深，不是算法精度问题 |

## 4. PC 界面：`tools/alg_tuner.py`

依赖：Python 3 + `pyserial`（tkinter 随 Python 自带）。

```bat
cd /d D:\FPGA_Project\imx219_pyrtl
python tools\alg_tuner.py --port COM5 --connect
```

`--port` / `--connect` 可以省：不带参数时下拉框会**自动挑第一个 FTDI/USB Serial 口**，
但要手动点"连接"。

**COM 口号不是固定的，别写死。** 同一块板的 FT4232H 第一次枚举成 COM5/COM6，
后来的 USB 重枚举变成 COM7/COM8，旧的那一对会作为 `Unknown` 死条目留在设备管理器里。
2026-09-27 实测（板子插上、烧完 `algo_uart_tuner_splitonly_20260926_2037.bit`）：

| 口 | 身份 | 现象 |
|---|---|---|
| **COM7** | FT4232H **channel C**（父设备 `USB Serial Converter C`，`MI_02`） | **每 500 ms 吐一行状态行** |
| COM8 | FT4232H channel D（`USB Serial Converter D`，`MI_03`） | 全程 0 字节 |
| COM3 / COM4 | **蓝牙**（`BTHENUM\{...}`），跟板子无关 | 别选 |

通道 A/B 被 D2XX 驱动占着（设备管理器"通用串行总线设备"下的 `Quad RS232-HS`，
Efinity 烧录走的就是 FTDI 接口），**不会**再出现成 COM 口 ——
所以设备管理器只列出 **2 个** USB Serial Port 是**正常**的，不用去找另外两个。

挑口的方法（都不用先知道编号）：

```bat
python tools\find_uart.py           :: 逐个试所有口，报出哪个在吐状态行
python tools\link_test.py COM7      :: 指定一个口跑 9 项链路测试
```

`alg_tuner.py` 的"无回读"提示出现时，九成就是选到 channel D 了。

- 顶部选串口（下拉框自动优先列 USB Serial / FTDI 设备），点"连接"。
- **每个参数一行**：中文名 + 滑块 + 本机值 + 「板端」回读值 + 单位/说明。
- 本机值与板端值一致 → **绿色**；不一致 → **红色**，状态栏列出差异。
- 拖动节流 60 ms，避免刷爆串口。
- 「全部下发」把当前所有滑块值重发一遍；「恢复默认 (R)」等价于 `R`；有日志区显示 TX/RX。
- 状态栏超过 1.5 s 没有回读会提示："串口选错了？板子没跑这个位流？"

## 6. 本检查点抓到的两个真 bug（记录以便复查）

1. `alg_cfg_uart.v` 的饱和累加器位宽不足：原来 `reg [12:0]` 只有 13 位，
   而 `2047*10+9 = 20479` 需要 15 位，导致比较 `> 4095` 永不成立，
   `T9999` 得到 1807 而非 2047。改为 `reg [15:0]` 后正确。
   **教训：饱和逻辑的中间变量必须能容纳未饱和的原始值。**
2. `alg_tuner.py` 用了 `ttk.Label.set()`（`ttk.Label` 不是 `StringVar`），
   一点滑块就 `AttributeError`。改为 `configure(text=...)`。
   **这个 bug 只有真的拖动滑块才会暴露，静态语法检查看不出来。**
3. 状态行从 60 字节扩到 65 字节（加 `EPS` 字段）时，`alg_cfg_telemetry.v`
   只改了 `MSG_LEN`，忘了改 `char_idx` 的位宽（还是 `reg [5:0]`）：64 装不
   进 6 位 → **LF 永远发不出来，而且行与行之间的 500 ms 间隔也没了**
   （计数器回卷 → 不停连发）。`tb_alg_cfg_uart` 当场报
   "telemetry line never matched"，改成 `reg [6:0]` 后 ALL PASS。
   **教训：改一个"长度"常量时，所有与它同宽的计数器/下标都要一起改。**
