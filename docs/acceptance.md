# 验收口径：我怎么判断"这张图好不好"

写这份东西的原因（板子持有人 2026-09-25 提问）：

> 我不知道你的判断逻辑是什么，不知道你怎么判断现在的图像和预期有多少差距，
> 不知道你是否真的能分辨出图像现在有哪些问题，有没有可能我看是很大问题、你看是很少问题。

**必须先承认：完全有可能。** 下面把我能判的、判不了的、已经判错过的一次次列清楚。

## 1. 我的判断分四层，可信度差得很远

### L0 事实层（最硬，不是"判断"，是数数）

时序、像素计数这类东西没有主观空间：`PIX=921600` 就是每帧 1280×720 个像素都过了一遍；
`THR=024 SH=8 ... CV=1 HY=1` 就是寄存器里真的存了这些值。这一层出错只会是**测量工具写错**，
不是"看法不同"。

### L1 赛题条款的可测代理（中等可信）

赛题 p25 原话："显示稳定，**无闪烁、无撕裂**"。这句话本身不可测，但它有可测的代理：

| 赛题原话 | 我的代理指标 | 为什么这个代理成立 |
|---|---|---|
| 无闪烁 | `toggle%` = 相邻帧右半边缘图逐像素翻转率的平均值 | 逐帧翻转就是闪烁的物理定义；测不了的是"人眼觉得闪" |
| 无撕裂 | （未实现）行间不连续检测 | 需要连续高速采样，我现在的采集口径做不到，见 §2 |
| 无丢帧、无错位 | `PIX` 计数、左右半边行对齐 | 计数与对齐是确定性的 |
| 阈值可参数化 | UART 命令 `T/S/D/E/C/H` + 按键 | 读回寄存器即可 |
| 用 DSP/移位加法，避免除法 | 综合报告里 DSP 占用、RTL 里无 `/` | 静态可查 |
| 实时（零延迟） | 数据路径里没有整帧缓存 | 看 RTL 结构；但 DDR 帧缓存是"约一帧"延迟，这条我**主动降级**了，见 `docs/contest_status.md` |

### L2 与参照视频同口径的可比数字（较弱，且经常不可比）

你说过参照视频就是目标。我把它的画面变成过统计画像（`docs/reference_video_analysis.md`）：
白线黑底、近二值、线条连续、平区干净、没有目标框。这是**风格目标**，不是逐像素目标。

关键限制：**同一张表里的数字经常不同口径，不能直接相减**。已经踩过一次：
参照视频是"手持相机拍屏幕"，我们是"HDMI 直采"，前者的帧间残差里混了相机抖动、
滚动快门、30 fps 采样拍频，所以参照那行 8.57% 被严重高估——那次我写下了口径警告，
而不是拿它去证明"我们比它好"。

### L3 只有你能判的（我判不了，也不该假装能判）

* 这张图"够不够用"、"好不好看"；
* 哪些细节必须保住（我按"lit% 掉到 1/3 换干净"是进步，你若认为信息量更重要，这就是退步）；
* 演示现场（光照、背景、评委的期待）下什么效果能过关。

**规则：L3 上出现分歧，以你为准，我改。** 我把你的判决记进下面的表格，
不拿 L1/L2 的数字去推翻你的眼睛。

## 2. 我的盲区（明确列出来，不装懂）

1. **我看不到快闪。** 采集卡实测 **23.4 fps**（板子输出 60 fps），采样率不够 → 高于
   约 11.7 Hz 的逐帧闪烁在我这里会**混叠**成慢速漂移甚至看不见。
   所以 "toggle% 从 8.4% 降到 1.6%" 只能说明**低频成分**确实少了，它**不能**保证 60 Hz 上不闪。
2. **彩色信息不可信。** 采集卡给的是 YUY2，色彩被降采样。红框能靠三通道同时高被识别出来，
   但"颜色好不好看"我判不了。
3. **我看不到真实的屏。** 我拿到的是采集卡的数字流，不是面板。屏的亮度、对比度、缩放
   （台面那台 1080p 屏会把 720p 拉成 1.5 倍）、拖影、视角全在屏上发生，我一次都看不到。
   你说"屏幕上有条线在闪"，我第一反应只能去抓帧找**数字流里的**那条线。
4. **我没有绝对审美，只会做相对比较。** 我能可靠回答的是"这一版比上一版好在哪"，
   不能可靠回答"这一版是不是达到目标了"。
5. **撕裂和延迟我测不了。** 都需要连续高速采样，23 fps 抓帧做不到。
6. **没见过的场景无法预测。** 我所有数字都来自固定场景的抓帧；换光照、换背景就要重测。
7. **我不知道评委在意什么。** 我只能引赛题原文，不能替评委定优先级。

## 3. 已经出现过的判断分歧与我的出错记录（证明这个担心是对的）

| 事 | 我当时怎么说 | 后来怎样 |
|---|---|---|
| 局部迟滞 | 先判断"弱边要跨行传播才能连接，硬件代价大" | **判错**。DOUDIU 那套是纯 3x3 局部组合逻辑，不需要跨行传播 |
| 第一轮板上 A/B | 当成有效数据在看 | **作废**。两次采样之间镜头前的内容变了，`lit%` 差 12 倍，量的是场景不是算法 |
| 迟滞的代价 | 记成"lit% 掉到 1/3~1/4，是可接受代价" | 这是我的**取舍标准**，不是你的。如果你要信息量，这一版就是退步 |
| 参照视频的 lit% | 一度想拿它当"目标值" | 那个框里 78% 是桌面背景，数字被污染，只能同量级比较 |

## 4. 我的改进办法：把"好"变成可核对的东西 + 你当唯一裁判

### 4.1 固定测试场景（而且它同时就是演示视频要拍的）

赛题 p25 明确写了演示对象："摄像头对着**简单几何图形**（如**黑白棋盘格**、**印有数字的纸张**、
**人脸轮廓**），展示边缘检测效果"。所以标准场景就用这三个——测试场景 = 演示场景，一举两得。

每个场景固定拍法：镜头对正、物体占画面一半以上、手持相机停稳 2 秒、连续抓 1.5 s。

### 4.2 每轮流程（你只需要 10 秒）

1. 我改代码 → 烧录（每次请你点头）；
2. 在同样三个场景各抓一段（脚本固定，不用你操作）；
3. 我出"上一版 / 这一版"并排图 + 指标表（存 `work/analysis/ab*/`）；
4. 你看一眼，只回答**更好 / 一样 / 更差**；
5. 我记进 §4.3 的表格，往上加一行。

规则：凡是你判"更差"的改动，要么回退，要么降级成 UART 可选开关而不是默认值。

## 5. 我请求你做的事（就三件）

1. **看着屏，随时插话。** 你看到任何"我数字里没有的毛病"，直接说——那一定是我盲区里的东西，
   我会把它写进 §2 并做新指标。
2. **给 L3 的判决。** 每次并排图出来，回我"更好/一样/更差"就够。
3. **定优先级。** §4.3 里 9~12 行哪几条要先做（我目前按赛题原文顺序推测，这只是推测）。
