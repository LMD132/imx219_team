# 3×3 中值滤波：网络正确性证据与 1 像素空间偏移

工具：`tools/verify_median_network.py`（纯离线，无板可跑）
被测 RTL：`rtl/median_filter_3x3_720p.v`（`generate` 排序网络 :164-184，抽头 :198）

## 1. 为什么值得单独验一次

板上那一级「中值」是整条链的第一道去噪。它若错，后面的高斯、Sobel、阈值、迟滞全部建立在
错的像素上，而且**错得很隐蔽**：中值网络错了，画面依旧是「看起来差不多」的边缘图，只是
噪点位置不对、细线被抹掉或留下，靠看截图根本判断不出来。

同时，网上流传的「3 周期中值」示波器式写法里，**三个数取反了**（下方 §4）。所以这里不能
引用「大家都是这么写的」当依据，必须自己量。

## 2. 我们的实现是什么

不是论文里的 5 步比较器树，而是**标准 9 相奇偶转置排序网络**：

```
sort_stage[0][0..8]  <- 九个窗口寄存器（top_left ... current）
for phase = 0 .. 8:     相邻奇偶对 compare-exchange，共 9 相
out_median_gray <- valid ? sort_stage[9][4] : raw_pipe[9]
```

奇偶转置排序对 **n 个数需要 n 相**才能完全排好，所以 9 个数正好要 9 相，第 5 个元素就是中值。
这不是「大概能行」，下面 PART A 里的相位计数就是这条主张的证据。

代价：9 相 + 1 级输出寄存器 = **10 拍像素延迟**（论文式 3 拍方法只要 3 拍），但每拍只有
1 个 8 位比较器在工作，时序余量很大；本工程主频 75 MHz，这点延迟在实时性上无所谓。

## 3. 证据（PART A + PART B，2026-09-26 实跑）

PART A —— 把 RTL 的 `generate` 循环逐字翻译成 Python，对同一组九宫格比「网络输出 == 排序后第 5 个」：

| 检查 | 规模 | 结果 |
|---|---|---|
| 穷举 4^9 全部窗口 | 262 144 | **0 失配** |
| 随机 8 位窗口 | 400 000 | **0 失配** |
| 相位深度 1..8 | 262 144 | 1..8 相分别错 167348 / 167348 / 167348 / 167348 / 114730 / 38316 / 8048 / **788** |
| 相位深度 9 | 262 144 | **0 失配** |

最后两行是重点：**8 相还不够，9 相才对**。也就是说 `sort_stage[9][4]` 这个深度是真需要的，
不是随手多给的。

PART B —— 按光栅顺序把同一网络跑在真实图像上（本次用 5 张抓帧的灰度图，逐像素推进寄存器），
再和 `cv2.medianBlur(..., 3)` 对比：

| 检查 | 规模 | 结果 |
|---|---|---|
| 网络输出 vs 同一窗口的 numpy 中值 | 4 588 020 窗口 | **0 失配** |
| 网络输出 vs `cv2.medianBlur` | 4 588 020 窗口 | **0 失配** |

结论：板上那一级**真的是中值滤波**，不是「某种排序后随便取的一个数」。

## 4. 顺带量到的两件事实

### 4.1 网上那版「3 周期中值」代码是错的

它算出每行的 `(min, med, max)` 后，取的是

```
min(row_mins) , med(row_meds) , max(row_maxes)   -> 再取这三个的中值
```

正确写法是**镜像**的三个数：

```
max(row_mins) , med(row_meds) , min(row_maxes)   -> 这三个的中值
```

在 4^9 穷举上，它**错 42 552 次（16.2 %）**。反例（原文自己举的九宫格）：

```
[1  2  100;  3  4  101;  102  103  104]
真中值 = 100，它的代码输出 = 4
```

我们的网络在这个窗口上输出 **100**，正确。CSDN 上那篇《中值滤波全解析》里的 5 步比较器树
写法是对的，在 4^9 上 **0 失配**——正好反证第 3 篇的错误。

### 4.2 中值流比灰度流「向左上一个像素」

寄存器链决定了窗口的九个值是 **行 y-2 / y-1 / y** × **列 x-2 / x-1 / x**，
所以窗口中心是 **(x-1, y-1)**，而不是 `(x, y)`。换算成光栅位置，这一级除了 10 拍流水之外
还多偏 **1 行 + 1 像素**。

这直接关系到彩色叠加：`rgb_delay_720p` 现在只补了 `4*1280 + 8` 个像素，**没把中值这 10 拍
算进水平偏移**，也没算其余各级的寄存器偏移。所以红边整体会**偏右十几像素**。修法是把像素
延迟做成 UART 可调（`P<n>`），上板扫出真正对齐的值，而不是继续靠估算。
