# 用采集卡把"画面观感"变成数字

## 为什么需要它

到目前为止，这条流水线唯一的验收盲区是**画面**：编译、时序、JTAG、串口遥测
都能自动核对，但"暗处的人轮廓够不够"只有板子持有人看一眼才能说。这个链路太慢，
也没法给赛题留下可量化的证据。

方案：**HDMI 采集卡**（USB，Windows 上就是 DirectShow 摄像头）接板子的 HDMI
输出，PC 端录屏，然后在 PC 上用与 RTL **逐行对应的整数流水线**复算一遍。这样：

- 我可以自己"看到"画面，不必每改一版都麻烦人描述；
- 阈值、去噪、前端增强都能用数字比较，而不是靠印象；
- 赛题要求"展示边缘检测效果"的演示视频（基础第 5 条）顺带解决。

## 硬件

任意 HDMI→USB 采集卡（UVC/DirectShow），支持 1280x720@60 即可。板上输出是
标准 720p HDMI，不加密，不需要 HDCP。

接法：`开发板 HDMI TX -> 采集卡 HDMI IN -> 笔记本 USB`

## 步骤一：找出采集卡是哪个设备

```
python tools\capture_hdmi.py --list
```

输出里每个设备一行。**本机 index 0 是笔记本自带摄像头（640x480）**，采集卡到
货后会是另一个 index，并且报告 `1280x720`。`--device` 不指定时脚本会自动挑
"报告 1280x720 的那个"，所以通常不用手填。

## 步骤二：录一段

> **测量之前先固定两样东西：摄像头和光源。** 2026-09-25 有一整轮 A/B 因为摄像头是
> 手持的而作废（见「第二轮 A/B」一节）：手持会让镜头相对光源的朝向不停变，整幅亮度
> 就能在十几秒里摆动 60 %，同时手抖让画面在相邻帧之间整片位移，`flick%` 冲到 74..90 %。
> 把 IMX219 模块架住 / 靠住，对准一个静止物体，光用房间灯或放在桌上的灯。任何
> "哪档更好"的排序都建立在这两条前提上，否则数字没有意义。

```
python tools\capture_hdmi.py --device 1 --seconds 6 --label dark_target --note "暗光下的人"
```

产物在 `work/capture/<label>/`：

- `clip.avi`：整段录像（MJPG，仅供回看）；
- `frame_XX.png`：抽出的 12 张无损静帧，分析用这个；
- `capture.txt`：设备号、分辨率、实测有效帧率、每张静帧的灰度均值/标准差。

实测有效帧率会打出来。板子是 720p60，如果这个数字长期低于 50，多半是采集卡
或 USB 带宽的问题，不是板子的问题——先解决采集端，再看画面。

## 步骤三：分析

```
python tools\analyze_capture.py --input work\capture\dark_target --dump work\analysis\dark_target --sweep
```

输出三类东西：

1. **每帧一行**：边缘占比、暗区占比、暗区里的边缘像素数、以及 min/max 外接框
   的位置和占屏比例；
2. **汇总**：上面几项的均值；
3. `--dump` 给出 `contact_sheet.png`：把输入灰度、当前板内结果、以及每个候选
   前端增强的结果并排贴成一张图，一眼能看出差别。

`--sweep` 会在一张静帧上把阈值 floor 从 4 扫到 96，用来判断"再降阈值还有没有
收益"以及"降到多低开始冒噪点"。

### 指标怎么读

| 指标 | 含义 | 关心它的原因 |
|---|---|---|
| `edge ratio` | 边缘像素占全帧比例 | 太低=边缘太稀（漏检）；太高=阈值太松/噪点 |
| `dark % of frame` | `gray < 64` 的像素占比 | 暗光场景的特征量 |
| `edges in dark` | 暗区里落了多少边缘像素 | **直接对应"暗目标轮廓少"这个抱怨** |
| `box % of frame` | min/max 外接框占屏面积 | 接近 100% 说明框已经"总是撑满屏"、失去意义 |

### 候选增强（同一套整数阈值，公平比较）

| 候选 | RTL 代价 | 说明 |
|---|---|---|
| `none` | 0 | 板子今天的样子 |
| `gamma 0.5/0.65/0.8` | 256x8 ROM | 抬暗部中间调，一个查表 |
| `mean-gain k=2/3` | 一个累加器 + 移位加法 | `out = mean + k*(in-mean)`，即参考工程 `vip_contrast` 的思路 |
| `histeq` | 256 bins + CDF，延迟一帧 | 全局直方图均衡，参考工程里的"治本"方案 |
| `clahe 2.0` | 不能用 | 局部均衡，只作为**上界参考**（RTL 装不下） |

⚠️ 注意：板内自适应阈值是 `max(center >> shift, floor)`。`shift=1` 时阈值正比
于局部亮度，所以**单纯整体提亮不一定有用**（阈值跟着一起涨）。这正是要用数字
而不是靠直觉来判断的地方。

## 复算为什么可信

`tools/analyze_capture.py` 里的每一步都能指到 RTL 的对应行：

| Python | RTL |
|---|---|
| `gray_bt601` | `median_filter_3x3_720p.v` 的 `(77R+150G+29B)>>8` |
| `cv2.medianBlur(3)` | 同模块 9 相奇偶排序取 element 4 |
| `sobel_magnitude` | `edge_display_720p.v` 的 `|Gx|+|Gy|` |
| `max(center >> shift, floor)` | `edge_display_720p.v` 的 `active_threshold` |
| `despeckle` | `edge_overlay_720p.v` 的"中心为 1 且邻域计数 >= DS" |

边界处理不同（板子在窗口越界处不产生边缘，OpenCV 用 `BORDER_REFLECT_101`），
所以复算时把最外一圈强制清零。

## 局限（必须知道）

1. **只有左半视野**：板子左半屏是原始灰度（摄像头画面的左半幅），复算用的就是
   它。要把目标落在左半幅里，或先切到"同视野并排"位流。
2. **采集卡会动灰度**：不少采集卡默认开自动增益/自动白平衡/色彩空间转换，会改
   分布。要么在采集卡里关掉，要么全程固定同一个设置（同一台卡、同一次供电），
   这样 A/B 对比仍然有效。
3. **优先 YUY2，别用 MJPG**：压缩会吃掉 1 像素宽的细边缘。脚本会先试 YUY2，
   不行才退回 MJPG（并在打印里说明用了哪个）。
4. 复算算的是**板内算法**，不含 DVI 编码和显示器；屏幕上看起来的抖动/撕裂属
   于显示时序问题，需要另判。

### 当前结论：卡、线、板子分别都是好的，失败只出现在板子到卡这一个组合

| 试验 | 结果 |
|---|---|
| 板子 HDMI TX → 新公对公线 → Dell D2421H | **有画面** → 板子输出与新线都好 |
| 笔记本 HDMI → 新线 → Dell D2421H | **有画面** → 笔记本口与新线都好 |
| 卡的 HDMI 输入接**另一台电脑**的输出 | **有输入、工作正常**（板子持有人 2026-09-25 验证） |
| 板子 HDMI TX → 新线 → 卡 | 无输入（卡输出自己的开机画面） |

三个部件各自单独测都能工作，唯一失败的是板子到卡 → **卡没坏**，是它不接受板子发出的
这种 TMDS 流。

⚠️ **修正一处误判**：早前把「笔记本 `Win+P` 里没有第二块屏」当成「卡没交 EDID」。
现在实测清楚了两件事：

- 这张卡**确实会向源端交 EDID**：Windows 的显示器列表里能看到
  `HJW2109 / UGREEN-UHD`（和笔记本内屏 `EDO0142` 并列），芯片大概率是 MS2109 系；
- 但它同时是 DirectShow 摄像头（抓帧走这条路），而且**是否真的被投出画面取决于
  `Win+P` 模式**。所以当时「`Win+P` 里没有第二块屏」只说明那时处于「仅电脑屏幕」，
  笔记本根本没往 HDMI 口输出，**不能**当成卡的证据——那次「笔记本 → 卡无输入」
  的观测因此作废。

### 怎么正确判断卡有没有收到信号

**采集卡永远不会出现在 Windows 的显示器列表里**，也不会被 `Win+P` 当成第二块屏——
它只是 DirectShow 视频设备。唯一正确的测法是：打开 Windows「相机」应用（或 OBS），
设备选 `UGREEN 25854`：

- 画面是卡自带的 UGREEN 开机/无信号画面 → 卡的 HDMI 输入没锁到信号；
- 画面是真实内容（桌面、板子的输出）→ 卡收到了。

所以「`Win+P` 里有没有第二块屏」「显示器设置里有没有新增显示器」这两条都不能用。

### 最可能的机理：板子输出是纯 DVI 风格，缺 AVI InfoFrame

`rtl/ti60f225_oob_top.v` 直接例化 `dvi_encoder`，只做 TMDS 编码：**没有 AVI
InfoFrame、没有音频、不理会 HPD/EDID**。Dell 这类正规显示器对 DVI 兼容性好，能直接
认下 720p60；而部分廉价采集卡（MS2109/MS2130 一类方案）要求源端给出 HDMI 的 AVI
InfoFrame 才肯锁定，纯 DVI 流会被它判成无信号。这与观测到的现象吻合。

已排除的其它可能：

- **时序非标**：不是。H = 1280+110+40+220 = **1650**，V = 720+5+5+20 = **750**，
  `hdmi_tx_slow_clk` 的 SDC period 13.468 ns = **74.25 MHz**，1650x750x60 = 74.25 MHz，
  就是 CEA-861 标准 720p60。
- **HDCP**：不是。全仓库检索 `hdcp` 零命中（唯一命中是 DDR3 加密核里的一段 base64
  文本），Dell 能直接显示这条流。产品页说这张卡不支持 HDCP、源端必须不加密，我们的源
  本来就不加密。
- **HPD/EDID 门控**：不是。我们的 TMDS 输出无条件常开，不等 HPD。

### 下一步（按顺序，最便宜的在前）

1. **确认接的是 `TX`（丝印 U17）**，不是 `RX`（U15）。两个口并排、大小一样，极易搞混；
   最好拍一张丝印照片存档。然后重试「板子 TX → 卡」。
2. 仍不行就中间**串一个 HDMI 分配器或切换器**再进卡：分配器会对 TMDS 重新整形并补上
   标准 HDMI 信号，是最便宜的一刀。
3. 仍不行就给 TMDS 加 **AVI InfoFrame**：`rtl/dvi_tx/` 里已有厂商 HDMI TX 组件
   （`auxiliary_video_information_info_frame.sv`、`packet_assembler.sv`、`audio_*.sv`、
   `ecc_calc_v1.v`），当前顶层并未使用它们。
4. 或者直接换一张**明确支持 DVI 输入**的采集卡。### 2026-09-25 复查：卡能打开，但拿到的是全黑帧

| 试验 | 结果 | 说明 |

抓帧用 `python tools\probe_uvc.py --device 1 --formats`（逐格式抓帧并 dump PNG）。### 实验 A 的结果：拔掉 HDMI 线

**卡并不是吐黑，而是显示它自己的「无信号 / No Signal」黄字画面**
（`docs/img/capture_no_signal.png`）：20 帧里能看到 1 帧带字，其余帧是纯黑，默认
640x480 下约 30 fps、720p MJPG 约 23 fps。

**与接板子时的对比**：

| 卡的 HDMI 输入 | 画面内容 | 实测帧率 |
|---|---|---|
| 空着（实验 A） | 偶尔出现「无信号 / No Signal」 | 23~30 fps |
| 接板子 TX | **40/40 帧纯黑，一帧 No Signal 都没有** | 约 5 fps |

有效画面，只能吐黑，而且帧率掉到 5 fps——像是接收端卡在"锁到时钟、解不出视频"的状态。
这与"板子发的是纯 DVI TMDS，卡锁到时钟却解不出 HDMI 视频"的假设一致。

要彻底把"板子信号的问题"和"卡接收路径的问题"分开，做实验 B：把同一根 HDMI 线改插
笔记本的 HDMI 输出（`Win+P` 选复制/扩展）再抓帧。### 实验 B 的结果：笔记本 HDMI → 卡 = 画面正常，卡这条链路全部通过

`Win+P` 选「扩展」之后，Windows 里出现两块**活动**显示器：

```
\\.\DISPLAY2  1440x960  primary=True    ← 笔记本内屏
\\.\DISPLAY1  1920x1080 primary=False   ← 采集卡（EDID 名 UGREEN-UHD）
```

抓到的就是笔记本的扩展桌面（黑壁纸 + 底部任务栏 + 时钟），见
`docs/img/capture_laptop_desktop.png`。实测帧率：640x480 约 30 fps、720p MJPG 约
23 fps、1080p MJPG 约 10 fps。

**结论：采集卡、HDMI 线、UVC 驱动、USB 链路、抓帧脚本，这一整条全部正常。**

于是到目前为止唯一失败的组合只剩一个：**板子 TX → 卡**。把实验 A/B 合起来看：

| 卡的 HDMI 输入 | 卡的表现 |
|---|---|
| 空着 | 显示自己的「无信号 / No Signal」 |
| 笔记本 HDMI（已确认在输出） | 正常画面 |
| 板子 TX | 一帧 No Signal 都没有，40/40 纯黑，帧率掉到 5 fps |

### 操作要点（省得重复踩）

- `Win+P` 必须选**扩展**或**复制**，Windows 才会真的往 HDMI 口输出；停在「仅电脑屏幕」
  时卡的输入侧什么都没有，会被误判成"卡收不到"。
- 抓帧前关掉 Windows「相机」应用，否则它独占设备。### 板子 TX → 卡：已知链路全好时的干净对比（2026-09-25）

先把 HDMI 线插回板子 `TX`（U17），并确认 Windows 只剩内屏一块活动显示器（即笔记本
那侧已断开，没有干扰），然后用与实验 A/B 相同的口径抓 40 帧 x 4 种格式：

| 格式 | 结果 | 帧率 |
|---|---|---|
| MJPG 1280x720 | 40/40 纯黑 | 5.6 fps |
| YUY2 1280x720 | 40/40 纯黑 | 4.8 fps |
| MJPG 1920x1080 | 40/40 纯黑 | 1.2 fps |
| 默认 640x480 | 40/40 纯黑 | 11.9 fps |

对照实验 A（线空着）在同一口径下是 640x480 约 29.9 fps 并且能看到「无信号」画面。
所以：**卡认得出板子那头有信号**（因此不再画 No Signal），但解不出画面；连帧率都被
拖低了一个数量级，像是接收端卡在"锁到时钟、解不出视频"的状态。故障在板子发出的
TMDS 上，与采集卡这一侧无关。

### 与厂商 HDMI TX demo 的配置对比（新线索）

翻板卡资料包发现厂商自己的 `03_hdmi_tx_demo\hdmi_tx_demo_v2`（彩条输出，有现成的
`outflow\hdmi_tx.bit`）：

- 它用的是**同一个** `rtl\hdmi_src\dvi_tx\dvi_encoder.v`，**同样没有 InfoFrame**
  （全工程检索 `infoframe` 零命中）——所以"缺 AVI InfoFrame"并不是我们独有的问题；
- 但它的 LVDS 配置里**三对数据线全部是 `vod="large"`**，而我们的设计里数据线是
  `vod="typical"`，只有时钟线是 `large`。

于是有两个便宜的下一步，按顺序：

1. **烧厂商的 `hdmi_tx.bit`（彩条）做对照**：卡能看到彩条 → "板子 HDMI TX + 这张卡"
   本身能通，问题落在我们与厂商参考设计的差异上；卡仍然全黑 → 这张卡就是不认这块板子的
   DVI 风格输出，得走加 InfoFrame 或换卡的路。
2. 把数据线 `vod` 改成 `large`（与厂商一致），重编译烧回再抓。### 厂商自己的 HDMI TX demo 也是全黑（关键对照）

把厂商的彩条 demo 烧上去（`03_hdmi_tx_demo\hdmi_tx_demo_v2\outflow\hdmi_tx.bit`，
用的是普通的 `dvi_encoder`），用同口径抓 30 帧 x 4 种格式：

| 格式 | 结果 | 帧率 |
|---|---|---|
| MJPG 1280x720 | 30/30 纯黑 | 4.6 fps |
| YUY2 1280x720 | 30/30 纯黑 | 4.6 fps |
| MJPG 1920x1080 | 30/30 纯黑 | 1.1 fps |
| 默认 640x480 | 30/30 纯黑 | 11.5 fps |

和我们自己的设计（5.6/4.8/1.2/11.9）几乎一模一样，而线空着时是 30 fps 并且能看到
「无信号」画面 —— 说明厂商 demo 同样在发信号、卡同样解不出。
**所以这不是我们 RTL 的问题。**

### 修正：我们的设计其实已经带 AVI InfoFrame

- 工程的编译列表里就有厂商 HDMI TX IP 的加密顶层 `rtl/dvi_tx/dvi_encoder.v_encrypted.v`，
  它的端口包含 `video_format`、`video_VIC`、`audio_L/R`、`audio_N`、`audio_CTS` 等，
  并且 `auxiliary_video_information_info_frame.sv`、`packet_assembler.sv`、`audio_*.sv`、
  `ecc_calc_v1.v` 也都在这份编译列表里；
- 我们 top 的接线与厂商自家的 HDMI 输出 demo
  （`10_Ti60f225_sc431hai2hdmi_demo\Ti60f225_sc431hai2hdmi_v1\rtl\ti60f225_oob_top.v`）
  **逐行一致**：同样 `.video_format(video_format)`、`.video_VIC(0)`、`.audio_N(6144)`，
  只有 `audio_CTS` 不同（74250 vs 148500）。

于是早前"我们缺 AVI InfoFrame、所以要加 InfoFrame"这条判断**作废**：这个差异并不存在。

### 剩下最可能的原因：物理层

厂商的普通 DVI demo 与我们的 HDMI IP 版本**都失败**，说明差别不在"发不发 InfoFrame"，
而在**这块板 TMDS 输出本身的电气特性**：TI60 是用 LVDS 仿 TMDS 驱动，对 Dell 这类带均衡
的正规显示器足够，但对廉价采集卡这类接收机偏"挑"。这与"卡不显示 No Signal、说明它认得
到有信号，但一帧都解不出来"的表现一致。

下一步两条腿走：

1. **免费试 RTL 变体**（每个约 3 分钟闭环：编译 -> JTAG -> 抓帧）：数据线 `vod` 由
   `typical` 提到 `large` 并把预加重调高；`video_VIC` 由 0 改成 16（标准 720p60 VIC）等；
2. **物理层最便宜的一刀**：板子与卡之间串一个 **HDMI 分配器 / 中继器**，让它把 TMDS
   重新整形、补成标准 HDMI 电平。### 两个免费的 RTL 变体都无效（2026-09-25）

按"物理层 vs 协议层"分不清，先把两个可改的 RTL/IO 变体各跑一遍（每条都是
编译 -> JTAG -> 抓帧 的完整闭环，位流归档在 `candidate_bitstreams/overlay_vod_large.bit`
与 `overlay_vic16.bit`）：

| 变体 | 改动 | 结果 |
|---|---|---|
| 1 | 三对 TMDS 数据线 `vod` 由 `typical` 提到 `large`（对齐厂商彩条 demo） | 30/30 全黑，4.6 / 4.6 / 1.1 / 11.4 fps |
| 2 | 变体 1 + `video_VIC` 由 0 改成 16（标准 720p60 VIC） | 30/30 全黑，4.7 / 4.7 / 1.2 / 10.8 fps |

两次的签名与基线完全相同（全黑、且卡不显示「无信号」、帧率被拖低一个数量级）。
**改 RTL 这条路性价比已经很低，两个变体都没有任何变化。**

结论范围收窄到：**这块板的 TMDS 输出与这张采集卡的输入之间的电气/兼容性**。同一块板
接 Dell 显示器正常，同一张卡接笔记本正常，两者一组合就解不出来；厂商自己的 HDMI TX
demo 同样如此。源文件已回退到验证过的基线状态，板子也烧回
`known_good` 同源的 `candidate_bitstreams/overlay_box.bit`。

下一步只剩两条（都不在 RTL 上）：

1. **板子和卡之间串一个 HDMI 分配器 / 中继器**（二三十到六十元）：重新整形 TMDS、
   补成标准 HDMI 电平，对"显示器能显示、采集卡不行"的命中率不低；
2. **换一张对 FPGA 这类 LVDS 仿 TMDS 输出更宽容的采集卡**。### 原理图证据：这块板的 HDMI TX 是"LVDS 直驱"，没有专用 TMDS 驱动

查板卡原理图 `Ti60F225A_V4_SCH.pdf` 第 12 张（HDMI TX 那页，连接器 U17）：

- `TX_TMDS_DATA_P2/N2`、`P1/N1`、`P0/N0`、`TX_TMDS_CLK_P/N` 从 FPGA（VCCOI03A bank）
  出发，**只经过 8 颗 50R 串阻（R166-R173）+ ESD 钳位（U26/U27 = RCLAMP0524P）
  就直接进连接器 U17**；
- 中间**没有** HDMI/TMDS 专用驱动或电平转换芯片；连接器的 **HPD/DDC/CEC 引脚全部没接**
  （图上打叉），这也印证了顶层"不理会 HPD/EDID"的设计；
- 连接器第 18 脚 +5V 由 `VCC_5V_TX`（经 L8 磁珠）提供，所以"卡缺 +5V"这条可以排除。

也就是说：这块板是用 FPGA 的 **LVDS 仿 TMDS**，差分幅度约 350 mV 量级，而不是 HDMI
规范的 400-600 mV。这解释了为什么 Dell 这类带自适应均衡、容差宽的正规显示器能吃住，
而廉价采集卡的接收机不行——也解释了为什么厂商自己的 HDMI TX demo 同样失败（同一套
TX 电路）。

注意：这条仍是"最符合全部观测的解释"，没有示波器看眼图就无法百分百证明根因是
"板子电平不够"还是"卡的接收太挑"。但两者都能被同一招解决：**中间串一个会重新整形、
并用标准 HDMI 发射机重发的分配器/中继器**。## ★ 通了：板子与采集卡之间串一个 HDMI 分配器（2026-09-25）

接法：`板子 TX (U17) -> 分配器 IN -> 分配器 OUT1 -> 采集卡 HDMI IN`，`OUT2 -> Dell`，
分配器插 USB 供电。

抓帧结果（每种格式 30 帧）：

| 格式 | 结果 | 帧率 |
|---|---|---|
| 默认 640x480 | **30/30 有画面**（全帧 mean 15.1） | 29.7 fps |
| MJPG 1280x720 | 部分黑帧（mean of means 4.2，后段有画面） | 23.2 fps |
| MJPG 1920x1080 | 部分黑帧（mean of means 10.7） | 6.7 fps |

抓到的就是板子的输出：**左半灰度 + 右半 Sobel 边缘 + 红框**，见
`docs/img/capture_via_splitter_720p.png`（板子那一刻对着的是一片很暗的场景，所以灰度
均值只有 15/255、边缘很稀——正好是"暗光下轮廓少"这个抱怨的现场证据）。

**结论：根因确认为电气/兼容性**（这块板用 FPGA 的 LVDS 直驱 HDMI TX，没有专用 TMDS
驱动）。中间串一个会重新整形、用标准 HDMI 发射机重发的分配器即可解决。
RTL 一侧的排查（vod、VIC、InfoFrame）到此全部翻篇，不需要再动。

**遗留问题**：720p / 1080p 下仍会出现间歇黑帧，只有 640x480 稳定；需要再调（换 USB
口、换格式、确认分配器供电稳定），好在 640x480 已经够做判读和计数。

## 公平 A/B：去噪级数 × 阈值 floor（2026-09-25，暗光）

要比的是「去噪级数 E0/E1/E2」和「阈值地板 floor」，两者都对噪声敏感，所以必须
在同一段静止画面里逐个切换、逐个抓帧，不能靠人眼记。工具是
`tools/live_sweep.ps1`（自己发 UART 命令、等待稳定、抓帧）和
`tools/analyze_sweep.py`（连通域 / 噪点 / 碎段 / 帧间闪烁），拼图落在
`docs/img/ab_compare.png`。评分只看右半边缘图（左半是灰度直通、x=640 是白色分隔
列），所以「亮点」的判据要求 R/G/B 三个通道同时 >140，顺带把分隔列排除掉。

灰度均值 21.4..21.8，场景静止，这一轮可信：

| 设置 | 灰度 | 密度% | 连通域 | 噪点(<=2px) | 碎段(3..39px) | 最大连通域 |
|---|---|---|---|---|---|---|
| E2 floor24（原默认） | 21.8 | 1.86 | 195 | 5 | 178 | 3049 |
| E2 floor20 | 21.6 | 2.45 | 84 | 1 | 50 | 3719 |
| **E2 floor16（新默认）** | 21.5 | 3.02 | **7** | **1** | **1** | 7340 |
| E2 floor14 | 21.5 | 3.17 | 9 | 3 | 1 | 7841 |
| E1 floor20 | 21.4 | 2.69 | 22 | 7 | 7 | 4711 |
| E0 floor20 | 21.5 | 3.02 | 105 | 83 | 19 | 12866 |

结论：

- **E2 + floor16 最优**：195 条碎段收敛成 7 条连通曲线，噪点仍然只有 1 个；回到

- floor 降到 14 开始冒噪点（3 个），升到 20/24 又碎开（50/178 段）。
- **关掉去噪（E0）最差**：83 个噪点，最大连通域 12866——噪点连成一片，已经不像

## 帧间稳定性：边缘图 18% 翻转是从哪来的（2026-09-25）

上一节那个「flick% 15..21%」查清了。方法：YUY2（未压缩）连抓 3 秒，按约 30 fps
抽样出 90 帧，比较**相邻**帧。

| 量 | 值 |
|---|---|
| 左半灰度直通（完全没经过 Sobel）逐像素平均 \|差\| | 3.86 LSB |
| 右半边缘图在相邻帧之间翻转的亮点比例 | 18.6 % |
| 整段灰度均值（首 -> 尾） | 20.19 -> 20.15（场景静止） |

结论：

1. **抖动来自传感器/采集链上游，不是边缘级引入的**：左半是没有经过任何算法的
   灰度直通，它自己相邻帧就差 3.86 LSB。
2. 边缘级只是把这种抖动**放大成二值翻转**：floor=16 附近，梯度值只要抖 ±2..3
   就跨过门限。所以总量是稳的（同一设定间隔 40 s 再抓，边缘总数只差 0.6%），
   只是「哪些点亮」一直在换。
3. 暗光下传感器增益拉满、灰度均值只有 20/255，信号极弱、噪声占比大。**光照好
   时这一项会明显好转**，这也是 demo 要挑好光线的直接原因。
4. 之前猜的「采集卡丢帧 / MJPEG 压缩噪声」不成立：卡实际跑在 YUY2（无损），而
   且比较的就是相邻帧。
5. 注意口径：抓帧只有约 23.6 fps（USB2 带宽上限），板上输出是 60 Hz，所以真屏
   上这种逐帧独立的噪声是以 60 Hz 在闪，比抓帧看到的更刺眼。

> **当天补正（先撤回、后恢复）**：这一节最初是在**摄像头被手持**的情况下量的（板子
> 持有人 2026-09-25 确认），当时本来准备把"归因于传感器噪声"这一步撤回。后来把摄像头
> 架住、光源固定重测了一遍，结论反过来了：
>
> - 相邻帧翻转率**没有下降，反而更高**（24..27 % 对当时的 18.6 %），所以手抖不是
>   翻转率的主因；
> - 对齐测试（零位移对齐的帧间差 4.82 LSB，平移 ±1 像素反而升到 11.3 / 21.1）证明
>   **画面根本没有移动**；
> - 分箱统计显示帧间差随局部对比度增长（平区 1.68 LSB -> 强对比 5.93 LSB），是**散粒
>   噪声**的形状。
>
> 所以这一节的归因**成立并已加强**，见后面的「帧间差到底长什么样」一节。手持真正
> 污染的是**光度**（整幅亮度六秒一档能摆 60 %），不是帧间翻转率。

可选缓解，按代价排序：

- **(a) 换更好的光**：零成本，直接压掉源头噪声。
- **(b) 二值图 3×3 多数表决**：只要 2 行 1-bit 行缓存（1280 bit ≈ 160 B），能杀
  掉孤立翻转点，杀不掉长轮廓上的翻转。
- **(c) 时域平均 3..5 帧**：根本解，需要 DDR 帧缓存往返，留给 phase 2。

## 传感器端还剩多少余量（寄存器审计，2026-09-25）

暗场这么吵，第一个该问的是"能不能从摄像头那边解决"。
`rtl/cam/piv2_720p_7M_2L_reg.mem` 是上电时一次性写进配置 RAM、再由 I2C 移出的
固定表；RTL 里没有任何 AE/AGC 模块（`rtl/cam/` 下只有 `piv2_config.v` 和
`i2c_phy.v`，全树搜 `auto_exp` / 增益相关也没有第二次写入）。所以**这两轮测量
里曝光和增益都是恒定的**，「有光那一轮 13% 的灰度漂移」不可能是相机自动曝光
造成的，只能是场景本身在变（灯、人、环境光）。参考组机制挡的正是这种人的动作。

表里最终生效的值：

| 寄存器 | 值 | 含义 |
|---|---|---|
| `0x0160/61` | 1763 | VTS，一帧多少行 |
| `0x0162/63` | 3448 | 行长度（pixel clock 数） |
| `0x015A/5B` | 1108 | 曝光（行） |
| `0x0157` | 0xC0 = 192 | 模拟增益 `256/(256-192)` = 4.0x |
| `0x0114` | 1 | MIPI 2 lane |
| `0x0164..0x0175` | — | 1920x1080 的读出窗口，输出 1280x720（`0x0172 = 3` 是 IMX219 这个模式的行合并） |

1763 x 3448 反推这个模式约 30 fps，一帧 33.3 ms，而曝光已经用掉 1108 行 =
**一帧的 62.9%**，模拟增益也已经拉到 4x。也就是说：

- **能动的余地很小**：曝光最多顶到 1759 行（VTS-4），信号 +59%、SNR 只 +2 dB，
  代价是运动模糊从 21 ms 变成一整个 33 ms 帧，对"实时边缘检测"的演示是坏交易。
- 满画面灰度均值只有 20/255，配上 4x 增益和 63% 的曝光，说明是**光子不够**
  （散粒噪声主导），不是我们的电路或阈值在制造噪声；再提模拟增益只会连同噪声
  一起放大。
- 所以**暗光这一项只能靠加光**，代码侧没有便宜的余量可捡。要验证"光照好了噪声
  就下去"，最直接的量法是带参照组的有光 A/B 里看 `flick%`。

另外记一笔口径：默认档最后一次用 `K` 命令把阈值交回按键控制，所以 `THR` 是
按键值，`SH`/`DS`/`EN` 来自复位后的默认（`SH=1 DS=3 EN=2` = 两级去噪）。

## 第二轮 A/B：摄像头是手持的，参照组判它作废（2026-09-25）

用修好的工具重跑了一轮八档（`E2 T12/T16/T20/T24` + `E1 T16` + `E0 T16`，首尾参照
`E2_T16`）。参照组 **14.1 -> 18.9（+33.6 %）**，是 5 % 判据的六倍多，工具直接判
`TOO MUCH - ranking not trustworthy`，这轮作废（评分产物
`work/analysis/ab_lit2.png`，别引用）：

| 抓帧 | refa | T12 | T16 | T20 | T24 | E1 | E0 | refz |
|---|---|---|---|---|---|---|---|---|
| 左半灰度 | 14.1 | 22.9 | 23.9 | 16.8 | 17.7 | 21.6 | 18.0 | 18.9 |

（与 `analyze_sweep.py` 打印的一致，取每档前两帧的均值。）

**原因：这一轮摄像头是板子持有人用手拿着的。** 手持会同时做两件坏事——镜头相对
光源的角度一变，整幅亮度就跳（上表 14..24 的来回摆）；手抖又让画面在相邻帧之间
整片位移，于是 `flick%` 冲到 74..90 %。这两条把全部现象解释完了，不需要再引入别的
假设。（我最初把"八张取景一致"读成"相机没动"，那是错的：整幅平移几个像素在缩略
拼图里根本看不出来，而整幅亮度对镜头朝向极其敏感。）

**所以定量测量之前有两个硬前提：摄像头固定、光源固定。** 把 IMX219 模块架住 /
靠住 / 贴住，对准一个静止物体，光用房间灯或放在桌上的灯。做不到这两条，光度漂移
和帧间翻转都测不出真值，任何 A/B 排序都不算数。

**上一节的结论因此撤回两条**：「每档内部灰度稳 = 场景静止」和「翻转率由场景的柔和
渐变决定」都是在手持条件下读的，不成立。同样是手持的嫌疑下，上午那个 `18.6 %`
也要重新看待——摄像头架住之后重测相邻帧翻转率：掉到百分之几就是手抖，仍在 15..20 %
才轮到传感器噪声和 floor 的解释。

## 帧间差到底长什么样：不是位移，是对比度相关的幅度噪声（2026-09-25）

`flick%` 一直压不下去，用两个测试定位它：

**一、画面是不是在动？** 用整幅平移对齐来试：零位移时帧间平均 `|差|` = **4.82 LSB**，
平移 ±1 像素反而涨到 11.3（水平）/ 21.1（垂直）。**画面根本没有移动**——摄像头是稳的，
采集卡也没有重采样抖动。

**二、差在哪？** 按第 0 帧的局部梯度幅值分箱，看帧间 `|差|`：

| 局部 \|梯度\| | 像素占比 | 帧间 \|差\| 均值 |
|---|---|---|
| 0..4（平区） | 5.0 % | **1.68 LSB** |
| 4..10 | 7.7 % | 2.21 LSB |
| 10..25 | 19.0 % | 4.01 LSB |
| 25..60 | 30.2 % | 5.14 LSB |
| > 60（强对比） | 38.1 % | **5.93 LSB** |

平区只有 1.68 LSB（这是读出噪声底），**越有对比的地方抖得越大**——噪声随信号走，
就是散粒噪声的形状，属于传感器端的物理噪声。它有个要命的后果：**真实边缘正好长在
对比度最高、也就是噪声最大的地方**，所以边缘本身在抖；抬高 floor 没法只删噪声、
留下边缘——floor 96 确实把 flick 压到 14.7 %，代价是只剩 1.66 % 的边缘。

**结论：这层闪烁不是电路的 bug，也调不掉。**（下一节确实在画面里找到了一层周期 2 像素的
固定图案，但它在**默认路径上正好被去噪器完全抵消** —— `[1,2,1]` 对周期 2 的序列是零响应
`(a+2b+a)/4 = (a+b)/2`。默认档 E2 的 Sobel 输入是干净的，所以这一节的三条路**照旧成立**；
那层图案是另一个独立的缺陷，只在灰度显示那一半上看得见。）

1. **加光**：散粒噪声按 `1/sqrt(光子数)` 下降，最便宜也最根本。上午灰度 20 时相邻帧
   差 3.86 LSB，现在灰度 60 时反而 4.81 LSB——绝对噪声随信号涨，但**相对**噪声
   （信噪比）是变好的，所以亮场景的绝对观感更稳。
2. **时域平均 3..5 帧**：根本解，需要 DDR 帧缓存往返，phase 2。
3. **接受它**：总能量是稳的（同设定两次抓帧边缘总数只差 1.8 %），数字上 25 % 很难看，
   但真屏观感还没让人评过——需要板子持有人在屏前给一句判断，再决定值不值得为它加
   帧缓存。

给演示档的建议：`floor` 24..32 是甜点（密度 7.1 -> 5.7 %、连通域 -20 %、噪点 -25 %），
既不像 16 那样碎，也不像 48 以上那样丢掉大片弱轮廓。

板子持有人指出：**静态截图看不出问题，要看长一点、当视频看**。这一条是对的，而且一试就

静态图看不出来，是因为这层图案**每一帧都在同一个位置**：任何一张截图都能看到它，但没有
任何一张截图能证明它"不动"。只有沿时间轴看，才能把它和"每帧都在变"的噪声分开。

### 二、RTL 走线对得上：灰度是拿 debayer 输出再算出来的

`rtl/ti60f225_oob_top.v`：

* `:971` 例化 `debayer_top_2to1`，输出 `rgb_datax2`（每个时钟 2 个 RGB 像素的并串流）；
* `:1003-1018` 用 `vid_cnt` 交替取 `[23:0]` / `[47:24]`，拆成单像素送到 `hdmi_tx_rdata`
  / `gdata` / `bdata`；
* `:1027` 把这些 RGB 送进 `median_filter_3x3_720p`，`:22-30` 做 BT.601 加权得到灰度；
* `:1130-1133` 左半显示的是**未去噪的 `raw_gray`**，右半 Sobel 吃的是 `den2_gray`。

这条链本身是"debayer 后的 RGB"。但一个已经 debayer 完的灰度图**应该是平滑的**，实测却在
2 像素这个尺度上剧烈交替，说明问题出在更前面：**`hdmi_tx_*data` 里已经带着棋盘格**了，
也就是 `debayer_top_2to1` 的 2:1 并串解复用存在相位/字节序错位。

### 三、边缘那一半：这就是屏上那些"线"

```
edge half: pixels lit >2%: 77227
  solid (>90%): 26126   flicker (10..90%): 35180   rare (2..10%): 15921
  -> 45.6 % of the lit pixels flicker
  columns carrying the most edge pixels: x=641(720), x=990(335), x=991(290) ...
```

棋盘格是 2 像素周期，水平一阶差分正好把它变成**成对的正负尖峰**（`rms |d1|` 22.88，远高于
噪声底 16），Sobel 就把它读成一条条**竖线**——这就是板子持有人在屏上看到的"一直有线"。

而"点在闪"是同一件事的另一面：棋盘格把每一列整体抬高或压低了几十 LSB，于是每列都骑在
阈值上，整列一起翻，`flick%` 就下不来（flicker 占点亮像素的 45.6 %）。

所以 `E0`（关去噪）那格能看见整片竖直条纹被点亮、`E2` 里基本清掉 —— 两级去噪压的其实
就是这个棋盘格，"每加一级去噪噪声指标减半"的真实对象是它，不是随机噪声。

### 四、这一节要修正的结论

上一节说"这层闪烁不是电路的 bug，也调不掉"，**这句错了**：

* 闪烁的直接原因是**画面里的固定图案把整列顶到门限附近**，不是散粒噪声（散粒噪声是真
  的，但它只是让结论看起来更自我一致）；
* 固定图案是**电路里可修的**，改 `debayer_top_2to1` 的相位/字节序就有可能整片消掉；
* 因而"为了闪烁必须加 DDR 帧缓存"这个推论先不做，修完棋盘格再复测 `flick%` 才有意义。

### 五、可信度边界（必须说清楚）

偶/奇列是 **2:1**（52.70 / 34.28），**不是**标准 Bayer 那种固定的恒定偏移。2:1 的比值
更像"两个增益不同的 CFA 通道"，或者并串解复用把两个通道错位拼接。所以：

* **铁证**：`hdmi_tx_*data` 路径上存在周期精确为 2 px 的通道不平衡；
* **强推断（尚非铁证）**：这条不平衡来自 `debayer_top_2to1` 的解复用相位与这块屏
  （1920×1080 窗口 -> 1280×720，`0x0172=3` 行合并）不匹配。

下一步就是去看 `debayer_top_2to1` 里 `rgb_datax2` 的字节序（`//b,g,r,b,g,r`）与 `vid_cnt`
相位，以及行合并对 CFA 相位的影响。这是目前唯一一处可能真的需要改 RTL 的地方。

## 两条 2 像素探针：那层条纹是可分离的乘法图案，上一节的 CFA 结论被推翻（2026-09-25）

上面那段把 2 px 图案归到 CFA / debayer 相位，是**推理**，而且错了。用两个探针直接量它的
结构（`tools/comb_probe.py`、`tools/comb_phase.py`，都是实时抓帧），
结论很清楚：这不是 Bayer 相位问题。

### 一、差值随亮度成比例：是乘法增益，不是固定偏移

按每对（偶列, 奇列）的局部亮度分箱，量对内的 `|d|`（`d = 右 - 左`）：

| 亮度区间 | 像素对 | `\|d\|` | `d` |
|---|---|---|---|
| 0..4 | 743293 | 2.44 | 2.14 |
| 8..12 | 1843247 | 6.64 | 5.97 |
| 16..24 | 3222312 | 10.21 | 9.42 |
| 32..48 | 4670373 | 16.48 | 15.63 |
| 64..96 | 1663170 | 42.90 | 42.77 |
| 128..192 | 39394 | 75.90 | 75.07 |

`|d|` 和 `d` 几乎相等，说明符号是**恒定**的（右亮左暗，不是噪声）；而且 `d / 均值` 一路
在 0.4..0.53 之间 —— **差值跟着亮度一起长**，所以是"偶列被乘了一个固定系数"（约 0.78）
"奇列约 1.22"，比值约 1.58，而不是一个固定偏移。垂直方向同构、幅度约一半（64..96 档
`|d|` = 19.98，上行亮）。

### 二、四个相位分解：可分离，不是棋盘格

把画面除以 4 像素盒均值（把 2 px 尺度以外的东西全部除掉，只剩图案），再按 (x 奇偶, y 奇偶)
四个相位分别求平均，0 表示"与局部均值一致"：

```
              x even      x odd
  y even    -0.1398    +0.3539
  y odd     -0.3286    +0.0574
  A_x = +0.2199    A_y = -0.1213    A_xy = -0.0269
```

也就是 显示亮度 ≈ 真值 × (1 + 0.22·(-1)^x) × (1 - 0.12·(-1)^y)；交叉项 -0.027 正好约等于
0.22×(-0.12) 那个乘积项，吻合。

**关键数字是 `A_xy` ≈ 0**：CFA 马赛克、Bayer 相位错位、以及任何"四个位置不等"的图案，都会把
几乎全部功率放进棋盘项 `A_xy`。实测 `A_xy` 只有 `A_x` 的 12 %，而 `A_x`、`A_y` 才是主项。

### 三、代数上也能证明它不可能来自 raw

在 RTL 那条 Malvar 路径上推：任一显示位置的亮度 = `0.299·wR + 0.587·wG + 0.114·wB`，而每个
位置三个通道都凑得齐（中心通道取原值，另外两个是插值）。于是在平坦灰场景下：

* **每通道增益**（R / Gr / Gb / B 任何一个不同）：四个相位的亮度**完全相等** —— 灰度里根本
  不会出现条纹，只会偏色。所以"白平衡/通道增益"这条路彻底排除。
* **与颜色无关的 raw 列增益**：四个相位变成 `(e,e)=(o,o)`、`(e,o)=(o,e)`，也就是**纯棋盘**，
  `A_xy` 占主导。实测正好相反。

两条都不成立，说明图案不是从 raw 进来的，而是加在**已经成型的画面**（raw 之后的灰度/图像数据）
上的。

### 四、红框和右半都干净，但这不能当"位置证据"

`tools/box_probe.py` / `y_probe.py`：红色的目标框（叠加层画的，在图像之后）没有
+22 % 的列项；右半的亮点（Sobel 边）`A_x = -0.001`，而灰度半是 `+0.233`。

**但这里有个陷阱**：右半的 Sobel 吃的是 `den2_gray`，而 `[1,2,1]` 对周期 2 是零响应。所以
"右半干净"只能说明**去噪器把图案吃掉了**，不能证明图案是编码器或采集卡加进去的。同理，
红框是 2 px 细线叠在带图案的背景上，它的局部均值会反过来带上背景的图案，读数带系统性偏差，
不能单独当结论用。

### 五、这一节修正了什么，没修正什么

* **修正**：图案不是 CFA / debayer 相位问题。它是**加在成型画面上的、可分离的乘法条纹**
  （+22 % 列 / -12 % 行）。
* **没修正**：默认档（E2）的 Sobel 输入是干净的，所以上一节"闪烁是散粒噪声、floor 调不掉"
  照旧成立。不要拿条纹去解释默认档的闪烁。
* **顺带发现的真实错位**：左半显示的像素来自 `raw_gray`（median 一级的 10 拍流水），而它的
  `vs/hs/de` 来自 `den2_*`（median + 两级 gauss）。`gauss3_720p` 每级是"两个时钟加两条行
  存储"（见该文件第 34-36 行的自述），所以右半比左半晚约 2 行 + 几个像素 —— 左右两半画的
  不是同一处场景，需要对齐。

### 六、仍未定案，下一步按代价排

1. **在真屏上确认"线"出现在哪一半**：左半（灰图，带条纹）还是右半（边缘图，带闪烁）。
   这一步只有板子持有人能做，而且它决定后面改哪里。
2. **把左半改成显示 `den2_gray`**（一行 RTL，`rtl/ti60f225_oob_top.v:1130-1132`）：既消掉
   竖纹，又顺手修掉上面那处延迟错位。注意这只是掩盖，不是根因。
3. **真根因**需要在板上抓一帧 `hdmi_tx_*data` 的灰度（偶/奇列对比），或看 `vid_cnt` 那一级
   2:1 拆包的相位在真实数据上对不对 —— 目前没有任何一条静态推理能定案，必须上板取数。

## 灰度半的条纹已经修掉（2026-09-25，已上板验证）

板子持有人确认"线"在**灰度半**，所以按第六节的第 2 条先做了显示侧修法：
`rtl/ti60f225_oob_top.v:1130-1132` 的 `in_r/in_g/in_b` 从 `raw_gray` 换成 `den2_gray`。
换的理由有两条，一次解决两个问题：

* `raw_gray` 还带着那层周期 2 像素的条纹，而 `den2_gray` 走完了整条去噪链；
* `raw_gray` 比 `den2_*` 的同步信号早约 2 行 + 几个像素，两半画的不是同一处场景。

编译 PASS（map/interface/pnr/pgm），最差 setup slack **+0.397 ns**，hold 正，JTAG 烧录成功
（`Device ID read from JTAG: 0x10660A79`）。

**验证**：同一台采集卡、同一分钟内用 UART 切 E0/E2 各抓 2 秒（同一场景、同一光线，可比）：

*改动前那一帧是另一个时刻抓的，当时画面里有一块很亮的区域，均值不可比；但 `A_x` 是相对量，
