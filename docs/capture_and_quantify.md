# 用采集卡把"画面观感"变成数字

## 为什么需要它

到目前为止，这条流水线唯一的验收盲区是**画面**：编译、时序、JTAG、串口遥测
都能自动核对，但"暗处的人轮廓够不够"只有板子持有人看一眼才能说。这个链路太慢，
也没法给赛题留下可量化的证据。

方案：**HDMI 采集卡**（USB，Windows 上就是 DirectShow 摄像头）接板子的 HDMI
输出，PC 端录屏，然后在 PC 上用与 RTL **逐行对应的整数流水线**复算一遍。这样：

- 我可以自己"看到"画面，不必每改一版都麻烦人描述；
- 阈值、去噪、前端增强都能用数字比较，而不是靠印象；
- 赛题要求"展示边缘检测效果"的演示视频（基础第 5 条）顺带解决。

## 硬件

任意 HDMI→USB 采集卡（UVC/DirectShow），支持 1280x720@60 即可。板上输出是
标准 720p HDMI，不加密，不需要 HDCP。

接法：`开发板 HDMI TX -> 采集卡 HDMI IN -> 笔记本 USB`

## 步骤一：找出采集卡是哪个设备

```
python tools\capture_hdmi.py --list
```

输出里每个设备一行。**本机 index 0 是笔记本自带摄像头（640x480）**，采集卡到
货后会是另一个 index，并且报告 `1280x720`。`--device` 不指定时脚本会自动挑
"报告 1280x720 的那个"，所以通常不用手填。

## 步骤二：录一段

```
python tools\capture_hdmi.py --device 1 --seconds 6 --label dark_target --note "暗光下的人"
```

产物在 `work/capture/<label>/`：

- `clip.avi`：整段录像（MJPG，仅供回看）；
- `frame_XX.png`：抽出的 12 张无损静帧，分析用这个；
- `capture.txt`：设备号、分辨率、实测有效帧率、每张静帧的灰度均值/标准差。

实测有效帧率会打出来。板子是 720p60，如果这个数字长期低于 50，多半是采集卡
或 USB 带宽的问题，不是板子的问题——先解决采集端，再看画面。

## 步骤三：分析

```
python tools\analyze_capture.py --input work\capture\dark_target --dump work\analysis\dark_target --sweep
```

输出三类东西：

1. **每帧一行**：边缘占比、暗区占比、暗区里的边缘像素数、以及 min/max 外接框
   的位置和占屏比例；
2. **汇总**：上面几项的均值；
3. `--dump` 给出 `contact_sheet.png`：把输入灰度、当前板内结果、以及每个候选
   前端增强的结果并排贴成一张图，一眼能看出差别。

`--sweep` 会在一张静帧上把阈值 floor 从 4 扫到 96，用来判断"再降阈值还有没有
收益"以及"降到多低开始冒噪点"。

### 指标怎么读

| 指标 | 含义 | 关心它的原因 |
|---|---|---|
| `edge ratio` | 边缘像素占全帧比例 | 太低=边缘太稀（漏检）；太高=阈值太松/噪点 |
| `dark % of frame` | `gray < 64` 的像素占比 | 暗光场景的特征量 |
| `edges in dark` | 暗区里落了多少边缘像素 | **直接对应"暗目标轮廓少"这个抱怨** |
| `box % of frame` | min/max 外接框占屏面积 | 接近 100% 说明框已经"总是撑满屏"、失去意义 |

### 候选增强（同一套整数阈值，公平比较）

| 候选 | RTL 代价 | 说明 |
|---|---|---|
| `none` | 0 | 板子今天的样子 |
| `gamma 0.5/0.65/0.8` | 256x8 ROM | 抬暗部中间调，一个查表 |
| `mean-gain k=2/3` | 一个累加器 + 移位加法 | `out = mean + k*(in-mean)`，即参考工程 `vip_contrast` 的思路 |
| `histeq` | 256 bins + CDF，延迟一帧 | 全局直方图均衡，参考工程里的"治本"方案 |
| `clahe 2.0` | 不能用 | 局部均衡，只作为**上界参考**（RTL 装不下） |

⚠️ 注意：板内自适应阈值是 `max(center >> shift, floor)`。`shift=1` 时阈值正比
于局部亮度，所以**单纯整体提亮不一定有用**（阈值跟着一起涨）。这正是要用数字
而不是靠直觉来判断的地方。

## 复算为什么可信

`tools/analyze_capture.py` 里的每一步都能指到 RTL 的对应行：

| Python | RTL |
|---|---|
| `gray_bt601` | `median_filter_3x3_720p.v` 的 `(77R+150G+29B)>>8` |
| `cv2.medianBlur(3)` | 同模块 9 相奇偶排序取 element 4 |
| `sobel_magnitude` | `edge_display_720p.v` 的 `|Gx|+|Gy|` |
| `max(center >> shift, floor)` | `edge_display_720p.v` 的 `active_threshold` |
| `despeckle` | `edge_overlay_720p.v` 的"中心为 1 且邻域计数 >= DS" |

边界处理不同（板子在窗口越界处不产生边缘，OpenCV 用 `BORDER_REFLECT_101`），
所以复算时把最外一圈强制清零。

## 局限（必须知道）

1. **只有左半视野**：板子左半屏是原始灰度（摄像头画面的左半幅），复算用的就是
   它。要把目标落在左半幅里，或先切到"同视野并排"位流。
2. **采集卡会动灰度**：不少采集卡默认开自动增益/自动白平衡/色彩空间转换，会改
   分布。要么在采集卡里关掉，要么全程固定同一个设置（同一台卡、同一次供电），
   这样 A/B 对比仍然有效。
3. **优先 YUY2，别用 MJPG**：压缩会吃掉 1 像素宽的细边缘。脚本会先试 YUY2，
   不行才退回 MJPG（并在打印里说明用了哪个）。
4. 复算算的是**板内算法**，不含 DVI 编码和显示器；屏幕上看起来的抖动/撕裂属
   于显示时序问题，需要另判。

### 当前结论：卡、线、板子分别都是好的，失败只出现在板子到卡这一个组合

| 试验 | 结果 |
|---|---|
| 板子 HDMI TX → 新公对公线 → Dell D2421H | **有画面** → 板子输出与新线都好 |
| 笔记本 HDMI → 新线 → Dell D2421H | **有画面** → 笔记本口与新线都好 |
| 卡的 HDMI 输入接**另一台电脑**的输出 | **有输入、工作正常**（板子持有人 2026-09-25 验证） |
| 板子 HDMI TX → 新线 → 卡 | 无输入（卡输出自己的开机画面） |

三个部件各自单独测都能工作，唯一失败的是板子到卡 → **卡没坏**，是它不接受板子发出的
这种 TMDS 流。

⚠️ **修正一处误判**：早前把「笔记本 `Win+P` 里没有第二块屏」当成「卡没交 EDID」。
现在实测清楚了两件事：

- 这张卡**确实会向源端交 EDID**：Windows 的显示器列表里能看到
  `HJW2109 / UGREEN-UHD`（和笔记本内屏 `EDO0142` 并列），芯片大概率是 MS2109 系；
- 但它同时是 DirectShow 摄像头（抓帧走这条路），而且**是否真的被投出画面取决于
  `Win+P` 模式**。所以当时「`Win+P` 里没有第二块屏」只说明那时处于「仅电脑屏幕」，
  笔记本根本没往 HDMI 口输出，**不能**当成卡的证据——那次「笔记本 → 卡无输入」
  的观测因此作废。

### 怎么正确判断卡有没有收到信号

**采集卡永远不会出现在 Windows 的显示器列表里**，也不会被 `Win+P` 当成第二块屏——
它只是 DirectShow 视频设备。唯一正确的测法是：打开 Windows「相机」应用（或 OBS），
设备选 `UGREEN 25854`：

- 画面是卡自带的 UGREEN 开机/无信号画面 → 卡的 HDMI 输入没锁到信号；
- 画面是真实内容（桌面、板子的输出）→ 卡收到了。

所以「`Win+P` 里有没有第二块屏」「显示器设置里有没有新增显示器」这两条都不能用。

### 最可能的机理：板子输出是纯 DVI 风格，缺 AVI InfoFrame

`rtl/ti60f225_oob_top.v` 直接例化 `dvi_encoder`，只做 TMDS 编码：**没有 AVI
InfoFrame、没有音频、不理会 HPD/EDID**。Dell 这类正规显示器对 DVI 兼容性好，能直接
认下 720p60；而部分廉价采集卡（MS2109/MS2130 一类方案）要求源端给出 HDMI 的 AVI
InfoFrame 才肯锁定，纯 DVI 流会被它判成无信号。这与观测到的现象吻合。

已排除的其它可能：

- **时序非标**：不是。H = 1280+110+40+220 = **1650**，V = 720+5+5+20 = **750**，
  `hdmi_tx_slow_clk` 的 SDC period 13.468 ns = **74.25 MHz**，1650x750x60 = 74.25 MHz，
  就是 CEA-861 标准 720p60。
- **HDCP**：不是。全仓库检索 `hdcp` 零命中（唯一命中是 DDR3 加密核里的一段 base64
  文本），Dell 能直接显示这条流。产品页说这张卡不支持 HDCP、源端必须不加密，我们的源
  本来就不加密。
- **HPD/EDID 门控**：不是。我们的 TMDS 输出无条件常开，不等 HPD。

### 下一步（按顺序，最便宜的在前）

1. **确认接的是 `TX`（丝印 U17）**，不是 `RX`（U15）。两个口并排、大小一样，极易搞混；
   最好拍一张丝印照片存档。然后重试「板子 TX → 卡」。
2. 仍不行就中间**串一个 HDMI 分配器或切换器**再进卡：分配器会对 TMDS 重新整形并补上
   标准 HDMI 信号，是最便宜的一刀。
3. 仍不行就给 TMDS 加 **AVI InfoFrame**：`rtl/dvi_tx/` 里已有厂商 HDMI TX 组件
   （`auxiliary_video_information_info_frame.sv`、`packet_assembler.sv`、`audio_*.sv`、
   `ecc_calc_v1.v`），当前顶层并未使用它们。

抓帧用 `python tools\probe_uvc.py --device 1 --formats`（逐格式抓帧并 dump PNG）。### 实验 A 的结果：拔掉 HDMI 线

**卡并不是吐黑，而是显示它自己的「无信号 / No Signal」黄字画面**

**与接板子时的对比**：

| 卡的 HDMI 输入 | 画面内容 | 实测帧率 |
|---|---|---|
| 空着（实验 A） | 偶尔出现「无信号 / No Signal」 | 23~30 fps |

`Win+P` 选「扩展」之后，Windows 里出现两块**活动**显示器：

`docs/img/capture_laptop_desktop.png`。实测帧率：640x480 约 30 fps、720p MJPG 约
23 fps、1080p MJPG 约 10 fps。

**结论：采集卡、HDMI 线、UVC 驱动、USB 链路、抓帧脚本，这一整条全部正常。**

于是到目前为止唯一失败的组合只剩一个：**板子 TX → 卡**。把实验 A/B 合起来看：

| 卡的 HDMI 输入 | 卡的表现 |
|---|---|
| 空着 | 显示自己的「无信号 / No Signal」 |

### 操作要点（省得重复踩）

- `Win+P` 必须选**扩展**或**复制**，Windows 才会真的往 HDMI 口输出；停在「仅电脑屏幕」
  时卡的输入侧什么都没有，会被误判成"卡收不到"。
- 抓帧前关掉 Windows「相机」应用，否则它独占设备。### 板子 TX → 卡：已知链路全好时的干净对比（2026-09-25）

先把 HDMI 线插回板子 `TX`（U17），并确认 Windows 只剩内屏一块活动显示器（即笔记本
那侧已断开，没有干扰），然后用与实验 A/B 相同的口径抓 40 帧 x 4 种格式：

| 格式 | 结果 | 帧率 |
|---|---|---|
| MJPG 1280x720 | 40/40 纯黑 | 5.6 fps |
| YUY2 1280x720 | 40/40 纯黑 | 4.8 fps |
| MJPG 1920x1080 | 40/40 纯黑 | 1.2 fps |
| 默认 640x480 | 40/40 纯黑 | 11.9 fps |

对照实验 A（线空着）在同一口径下是 640x480 约 29.9 fps 并且能看到「无信号」画面。
所以：**卡认得出板子那头有信号**（因此不再画 No Signal），但解不出画面；连帧率都被
拖低了一个数量级，像是接收端卡在"锁到时钟、解不出视频"的状态。故障在板子发出的
TMDS 上，与采集卡这一侧无关。

### 与厂商 HDMI TX demo 的配置对比（新线索）

翻板卡资料包发现厂商自己的 `03_hdmi_tx_demo\hdmi_tx_demo_v2`（彩条输出，有现成的
`outflow\hdmi_tx.bit`）：

- 它用的是**同一个** `rtl\hdmi_src\dvi_tx\dvi_encoder.v`，**同样没有 InfoFrame**
  （全工程检索 `infoframe` 零命中）——所以"缺 AVI InfoFrame"并不是我们独有的问题；
- 但它的 LVDS 配置里**三对数据线全部是 `vod="large"`**，而我们的设计里数据线是
  `vod="typical"`，只有时钟线是 `large`。

于是有两个便宜的下一步，按顺序：

1. **烧厂商的 `hdmi_tx.bit`（彩条）做对照**：卡能看到彩条 → "板子 HDMI TX + 这张卡"
   本身能通，问题落在我们与厂商参考设计的差异上；卡仍然全黑 → 这张卡就是不认这块板子的
   DVI 风格输出，得走加 InfoFrame 或换卡的路。
2. 把数据线 `vod` 改成 `large`（与厂商一致），重编译烧回再抓。### 厂商自己的 HDMI TX demo 也是全黑（关键对照）

用的是普通的 `dvi_encoder`），用同口径抓 30 帧 x 4 种格式：

| 格式 | 结果 | 帧率 |
|---|---|---|
| MJPG 1280x720 | 30/30 纯黑 | 4.6 fps |
| YUY2 1280x720 | 30/30 纯黑 | 4.6 fps |
| MJPG 1920x1080 | 30/30 纯黑 | 1.1 fps |
| 默认 640x480 | 30/30 纯黑 | 11.5 fps |

和我们自己的设计（5.6/4.8/1.2/11.9）几乎一模一样，而线空着时是 30 fps 并且能看到
「无信号」画面 —— 说明厂商 demo 同样在发信号、卡同样解不出。
**所以这不是我们 RTL 的问题。**

### 修正：我们的设计其实已经带 AVI InfoFrame

- 工程的编译列表里就有厂商 HDMI TX IP 的加密顶层 `rtl/dvi_tx/dvi_encoder.v_encrypted.v`，
  它的端口包含 `video_format`、`video_VIC`、`audio_L/R`、`audio_N`、`audio_CTS` 等，
  并且 `auxiliary_video_information_info_frame.sv`、`packet_assembler.sv`、`audio_*.sv`、
  `ecc_calc_v1.v` 也都在这份编译列表里；
- 我们 top 的接线与厂商自家的 HDMI 输出 demo
  （`10_Ti60f225_sc431hai2hdmi_demo\Ti60f225_sc431hai2hdmi_v1\rtl\ti60f225_oob_top.v`）
  **逐行一致**：同样 `.video_format(video_format)`、`.video_VIC(0)`、`.audio_N(6144)`，
  只有 `audio_CTS` 不同（74250 vs 148500）。

于是早前"我们缺 AVI InfoFrame、所以要加 InfoFrame"这条判断**作废**：这个差异并不存在。

### 剩下最可能的原因：物理层

厂商的普通 DVI demo 与我们的 HDMI IP 版本**都失败**，说明差别不在"发不发 InfoFrame"，
而在**这块板 TMDS 输出本身的电气特性**：TI60 是用 LVDS 仿 TMDS 驱动，对 Dell 这类带均衡
的正规显示器足够，但对廉价采集卡这类接收机偏"挑"。这与"卡不显示 No Signal、说明它认得
到有信号，但一帧都解不出来"的表现一致。

下一步两条腿走：

1. **免费试 RTL 变体**（每个约 3 分钟闭环：编译 -> JTAG -> 抓帧）：数据线 `vod` 由
   `typical` 提到 `large` 并把预加重调高；`video_VIC` 由 0 改成 16（标准 720p60 VIC）等；
2. **物理层最便宜的一刀**：板子与卡之间串一个 **HDMI 分配器 / 中继器**，让它把 TMDS
   重新整形、补成标准 HDMI 电平。### 两个免费的 RTL 变体都无效（2026-09-25）

按"物理层 vs 协议层"分不清，先把两个可改的 RTL/IO 变体各跑一遍（每条都是
编译 -> JTAG -> 抓帧 的完整闭环，位流归档在 `candidate_bitstreams/overlay_vod_large.bit`
与 `overlay_vic16.bit`）：

| 变体 | 改动 | 结果 |
|---|---|---|
| 1 | 三对 TMDS 数据线 `vod` 由 `typical` 提到 `large`（对齐厂商彩条 demo） | 30/30 全黑，4.6 / 4.6 / 1.1 / 11.4 fps |
| 2 | 变体 1 + `video_VIC` 由 0 改成 16（标准 720p60 VIC） | 30/30 全黑，4.7 / 4.7 / 1.2 / 10.8 fps |

两次的签名与基线完全相同（全黑、且卡不显示「无信号」、帧率被拖低一个数量级）。
**改 RTL 这条路性价比已经很低，两个变体都没有任何变化。**

结论范围收窄到：**这块板的 TMDS 输出与这张采集卡的输入之间的电气/兼容性**。同一块板
接 Dell 显示器正常，同一张卡接笔记本正常，两者一组合就解不出来；厂商自己的 HDMI TX
demo 同样如此。源文件已回退到验证过的基线状态，板子也烧回
`known_good` 同源的 `candidate_bitstreams/overlay_box.bit`。

下一步只剩两条（都不在 RTL 上）：

1. **板子和卡之间串一个 HDMI 分配器 / 中继器**（二三十到六十元）：重新整形 TMDS、
   补成标准 HDMI 电平，对"显示器能显示、采集卡不行"的命中率不低；
2. **换一张对 FPGA 这类 LVDS 仿 TMDS 输出更宽容的采集卡**。
